# Archive Git Guide

## 1. Purpose

本 skill 用于帮助 **B 端供应链系统产品经理** 在一个版本或 demo 阶段收口时，做好：

- 版本归档
- 变更留痕
- 提交说明
- Git 同步

它的目标不是做“发布运维”，而是确保模板工程中的文档、原型资产和主档更新能被清楚追溯。

## 2. Default Context

默认适用于以下场景：

- 一个版本文档已经写完，准备归档
- 一个 demo 已经完成，准备收口
- 主档已经更新，准备留痕提交
- 需要把版本产出稳定推送到仓库

## 3. Core Goal

本 skill 的核心目标是保证每次版本收口都做到：

1. 版本目录是完整的
2. 主档更新是清楚的
3. 归档位置是明确的
4. 提交信息是可追溯的

## 4. Closeout Checklist

在归档和提交前，优先检查以下内容：

- 当前版本目录是否完整
- `05_PRD_Final.md` 是否已定稿
- `04_Prototype_Notes.md` 是否已补齐
- `Audit_Reports/` 是否已保存
- 若有稳定结论，是否已同步到 `01_Master_Documents/`
- 是否混入了与本次版本无关的临时文件

## 5. Archive Rules

### 5.1 版本目录归档

- 版本目录必须与版本号一一对应
- 版本内文件应按既定顺序保留
- 归档前不要临时改名或塞入杂项文件

### 5.2 原型资产归档

- 截图、图文说明、原型记录应和版本关联
- 如果是特定版本生成的演示资产，优先放入版本目录下的 `Prototype_Archive/`

### 5.3 主档留痕

- 如果本次版本已经沉淀出稳定结论，应同步更新主档
- 主档更新后，应保证修订记录和版本状态可回查

## 6. Commit Rules

提交前应满足：

- 变更范围清晰
- 提交内容属于同一批目的
- 不混入无关草稿、测试文件或临时截图

提交说明应至少体现：

- 这次改了什么
- 这次属于整理、归档、替换，还是版本收口

## 7. Good Output Standard

一次合格的版本收口，应该满足：

- 别人能看懂这次版本交付了什么
- 别人能看懂主档更新了什么
- 别人能在 Git 记录中快速回溯本次动作
- 以后回看时，不会搞不清哪个版本对应哪些资产

## 8. Anti-Pattern

以下做法应尽量避免：

- 一个提交里混入多种无关目的
- 版本目录不完整就直接归档
- 主档改了但没有说明
- 把临时文件、测试文件混入正式提交
- 只提交结果，不保留过程资产

## 9. Next Suggested Actions

完成版本归档和 Git 收口后，推荐进入以下任一步：

1. 更新 `Dashboard.md` 中的版本状态
2. 检查是否需要继续开启下一版本
3. 将本次版本作为后续 demo 基线
