# Mermaid Engine

## 1. Purpose

本 skill 用于帮助 **B 端供应链系统产品经理** 把复杂的业务逻辑、流程关系、状态变化和模块结构画成可读图。

它的目标不是“把图画复杂”，而是让文档中的核心逻辑满足：

- 一眼能看出流程走向
- 一眼能看出状态变化
- 一眼能看出模块关系
- 一眼能看出异常分支

## 2. Default Context

默认适用于以下图类型：

- 页面流转图
- 业务流程图
- 状态流转图
- 模块关系图
- 主档架构图

默认适用于以下场景：

- `03_PRD_Initial.md`
- `05_PRD_Final.md`
- `Product_Architecture.md`
- `Module_Map.md`
- demo 说明文档

## 3. Diagram Selection Rule

### 3.1 页面或流程路径

优先使用：

- `graph TD`
- `flowchart TD`

适用于：

- 用户从哪一步进入
- 接下来会走哪几步
- 哪些条件会分叉

### 3.2 状态变化

优先使用：

- `stateDiagram-v2`

适用于：

- 订单状态变化
- 调度状态变化
- 入库/出库状态变化
- 异常处理状态变化

### 3.3 模块关系或主档拓扑

优先使用：

- `graph TD`

适用于：

- 模块之间的上下游关系
- 主档中的结构关系
- 业务链路中的层次关系

## 4. Core Rules

### 4.1 通用规则

- 严禁用 ASCII 假图替代 Mermaid
- 每张图只表达一个核心问题，不要混太多目标
- 图前要说明“这张图是干什么的”
- 图后要补一句关键解释，避免只扔图不说明

### 4.2 流程图规则

- 起点和终点要清楚
- 分叉条件要明确
- 节点名称优先使用业务动作或业务状态
- 如果存在异常分支，必须画出来

### 4.3 状态图规则

- 必须包含明确的初始状态
- 状态名称必须能被业务方理解
- 每条状态切换都应标注触发动作或触发条件
- 至少要补一个异常或退回分支

### 4.4 模块图规则

- 主模块放中间或主线位置
- 上游、下游、支撑模块尽量分层
- 不要把所有模块画成同等重要

## 5. Supply Chain Diagram Focus

供应链场景下，优先画清楚这些内容：

- 流程起点和终点
- 状态推进顺序
- 异常触发点
- 责任边界
- 上下游协同关系
- 时间敏感节点

## 6. Anti-Pattern

以下画法应尽量避免：

- 图里节点太多，看不出主线
- 状态图只有正常流，没有异常流
- 模块图没有层级，全部堆在一起
- 图画完后没有文字解释
- 节点名称写成只有内部人才懂的缩写

## 7. Good Output Standard

一张合格的 Mermaid 图，应该满足：

- 业务方能顺着箭头看懂逻辑
- 评审者能快速看出主线和异常线
- 能直接服务 PRD、主档或 demo 讲解
- 图和文字说明能互相补充，而不是互相重复
