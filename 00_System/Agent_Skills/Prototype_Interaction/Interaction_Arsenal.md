# Interaction Arsenal

## 1. Purpose

本 skill 用于帮助 **B 端供应链系统产品经理** 在做原型说明、页面设计和 demo 展示时，使用一套稳定的后台交互表达规则。

它的目标不是追求“设计感”本身，而是让页面表达满足：

- 看得清
- 找得到
- 讲得顺
- 能支撑业务闭环演示

## 2. Default Context

默认适用于以下页面类型：

- 列表页
- 详情页
- 审批或处理页
- 调度、仓储、运输、异常跟踪等操作页面
- dashboard 或状态看板页

默认适用于以下场景：

- 内部评审
- demo 演示
- PRD 初稿页面表达
- 原型结构说明

## 3. Core Rules

### 3.1 列表页表达

- 多条记录优先使用表格型结构
- 筛选区、结果区、操作区必须分层清楚
- 高价值字段要前置，低频字段不要挤在首屏
- 如果存在状态、异常、优先级，必须让这些信息能一眼看见

### 3.2 详情页表达

- 详情页优先先讲“当前状态”和“下一步动作”
- 关键业务信息要先于补充信息出现
- 详情区不要只堆字段，要有分组和层次

### 3.3 表单与处理页表达

- 字段过多时必须分组或分步
- 必填项、异常项、风险项必须显眼
- 录入动作和提交动作要清楚分开

### 3.4 状态与反馈表达

- 加载、成功、失败、空状态必须可见
- 危险操作必须有二次确认
- 异常反馈必须说清楚“为什么失败”和“接下来怎么办”

### 3.5 Demo 表达规则

- 一次 demo 页面不要承载太多目标
- 演示页面优先保留主链路相关信息
- 如果一个页面只是支撑流程，不要过度设计成主角页面

## 4. Typical Supply Chain Patterns

在供应链后台场景下，优先使用以下表达模式：

### 4.1 状态可见

- 订单状态
- 调度状态
- 入库/出库状态
- 异常处理状态
- 对账或结算状态

这些状态必须前置，不能埋在详情底部。

### 4.2 异常优先

- 有异常的记录应当明显区别于正常记录
- 异常入口要比普通详情入口更容易发现

### 4.3 协同边界清晰

- 谁处理
- 谁确认
- 谁驳回
- 谁等待上游或下游

这些边界必须在页面中表达清楚。

### 4.4 时间敏感信息前置

- 时效要求
- 超时风险
- 截止时间
- 最近更新时间

供应链场景中，这类信息优先级很高，不应后置。

## 5. Anti-Pattern

以下表达方式应尽量避免：

- 把筛选区、表格区、操作区混成一团
- 一个页面同时展示太多目标
- 状态很多，但没有主次层级
- 异常提示只写“失败了”
- demo 页面塞满信息，导致听众无法抓住主线

## 6. Good Output Standard

一个合格的交互表达结果，应该满足：

- 能一眼看出页面主要任务
- 能一眼看出当前状态和关键异常
- 能支持讲解者顺着主线往下讲
- 能让评审者快速判断信息层级是否合理
