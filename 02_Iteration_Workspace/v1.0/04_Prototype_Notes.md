## 3. 演示说明

### 3.1 本次 demo 目标

- 验证货主侧用户是否能顺着同一条主线完成“订单导入 -> 整车/零担规划 -> 承运商指派 -> 生成运输任务”。
- 验证承运商推荐是否能展示出可信的决策依据，而不是只是点选列表。

### 3.2 主要受众

- 业务部门负责人
- 物流管理负责人

说明：
本次演示重点应放在“货主侧决策效率和运输编排透明度”上，而不是系统实现细节。

### 3.3 建议演示顺序

1. 从订单池进入，说明订单如何进入待规划状态。
2. 进入运输规划页，说明为什么需要先做合单、拆单或路线判断。
3. 展示承运商推荐区，重点讲清成本、时效、运力可用性三类依据。
4. 确认指派后，进入运输任务生成结果页，说明闭环已经成立。

### 3.4 页面级演示重点

#### 页面 1：订单池 / 待规划列表
- 要重点讲：哪些订单进入待规划状态。
- 要让听众看到：筛选能力、整车/零担标签、是否可进入规划的状态差异。

#### 页面 2：整车/零担规划页
- 要重点讲：为什么订单需要先做规划判断，而不是直接选承运商。
- 要让听众看到：FTL 主线和 LTL 对照场景在同一页中的分层表达。

#### 页面 3：承运商推荐区
- 要重点讲：推荐不是拍脑袋，而是有依据。
- 要让听众看到：KPI、报价、市场参考价、偏差提示、排序切换。

#### 页面 4：任务生成结果页
- 要重点讲：本次闭环已经成立。
- 要让听众看到：任务编号、承运商、状态、后续可跟踪入口。

### 3.5 本次必须强调的点

- 这是货主控制塔视角下的国内陆运场景，而不是承运商执行视角。
- 承运商推荐不是拍脑袋，而是有明确依据。
- demo 重点在“决策闭环”，不是“执行闭环”。
- FTL 作为主演示线，LTL 在同一规划页中作为补充对照区块出现。

### 3.5A 页面表达约束

- 页面文案应优先服务业务评审和调度决策理解，避免过度平台化、算法化或“大中台”叙事。
- 页面 1 不将前程陆运做成主筛选入口或主操作路径。
- 页面 2 不将前程陆运做成主规划驱动，只保留为特殊说明或低频例外信息。
- 页面 4 不将前程陆运或系统回写联动做成结果页主叙事，结果页应优先突出任务生成成功和后续入口。

### 3.6 本次暂不展开的点

- 司机端执行流程
- 在途监控完整过程
- 签收回单闭环
- 费率对账闭环

### 3.7 当前待定问题

- 前程陆运说明在本次 demo 中展示到什么粒度最合适

### 3.8 推荐依据展示优先级

- 第一优先：成本
- 第二优先：时效
- 第三优先：运力可用性

说明：
本次 demo 以“货主决策闭环”为主，因此推荐依据应优先体现最能支撑选择的三类信息，不展开过多低频指标。

### 3.9 推荐排序规则

- 默认排序：综合评分优先
- 可切换排序：报价最低 / 时效最优 / KPI 最优
- 演示重点：先展示系统默认推荐，再说明人工切换排序后的差异

### 3.10 场景锁定

- 主场景：工厂到工厂内贸运输
- 支线说明：出海前程陆运
- 演示原则：主场景必须完整讲通；支线场景通过“场景标签/订单类型标签”提示系统兼容能力，不单独展开完整主线

### 3.11 前程陆运支线规则

- 支线说明方式：不单独拉流程，只保留一条规则说明
- 关键规则：若订单属于前程陆运场景，推荐逻辑必须先校验是否满足截关时间；若不能满足，即使报价更低，也不能作为默认优先推荐
- 展示边界：前程陆运优先停留在承运商推荐页的规则说明和候选降级逻辑中，不前置扩散到全部页面的主信息层

### 3.12 原型回对原则

- 原型工具生成结果仅作为候选表达，不等同于最终业务口径。
- 若原型与 `PRD`、`Prototype Notes`、`Page Spec` 冲突，以当前版本文档中已锁定的业务边界和规则为准。
- 原型走查时，应优先检查：主场景是否仍为工厂到工厂内贸运输、前程陆运是否仍为说明性支线、推荐页是否仍符合“截关优先于低价”的规则。
