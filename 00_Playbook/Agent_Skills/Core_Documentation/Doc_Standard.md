# Markdown Standard

## 1. Purpose

本 skill 用于统一 `TMS_Shipper` 模板工程中的文档排版和信息表达方式。

重点适用于：

- `01_Master_Documents/`
- `02_Iteration_Workspace/`
- demo 说明文档
- 图文操作说明

目标不是追求花哨，而是让文档满足：

- 一眼能看懂结构
- 一眼能看出重点
- 一眼能分清主次

## 2. Default Context

默认适用于以下文档类型：

- 问题定义类文档
- 竞品研究类文档
- PRD 初稿与终稿
- 原型说明
- 主档、模块地图、决策日志、看板
- 图文操作说明

## 3. Core Rules

### 3.1 标题层级

- 严禁跳级使用标题
- 一个文档内的标题层级应稳定
- 标题名称尽量短，优先表达功能，不写空泛口号

### 3.2 信息分块

- 超过 3 条并列信息，优先改成列表
- 条件、结果、异常、动作的对应关系，优先改成表格
- 一段只表达一个主意思，不要把多个逻辑揉成一段长文字

### 3.3 重点高亮

- 核心状态、关键字段、按钮名、版本号、文件名，应适度高亮
- 高亮方式优先使用：
  - 内联代码
  - 加粗
- 不要整段大面积加粗，避免重点失焦

### 3.4 图表与结构图

- 逻辑链路、状态流、模块关系，优先使用 Mermaid
- 图前要有一句说明“这张图是干什么的”
- 图后如有关键结论，也应补一句文字说明

## 4. Document-Type Suggestions

### 4.1 问题定义与研究文档

- 优先使用短段落 + 列表
- 结论区单独成段
- 证据来源不要埋在正文中间

### 4.2 PRD 文档

- 页面结构、模块结构、交互规则要分区写
- 异常处理和边界条件要单独成块
- 多个动作点应尽量用表格呈现

### 4.3 主档文档

- 主档优先追求稳定结构
- 新增内容时尽量延续原有节奏和层级
- 修订记录、版本状态、模块清单建议固定位置

### 4.4 图文说明文档

- 一步一图或一步一段，不要让用户来回跳读
- 每步至少说明：做什么、看到什么、结果是什么

## 5. Writing Style Rules

- 优先写业务语言，不写技术黑话
- 优先写结论，再写说明
- 优先写动作，再写背景
- 能简短就简短，但不能省掉关键边界

## 6. Anti-Pattern

以下写法应尽量避免：

- 标题层级混乱
- 一个段落写太多意思
- 大片没有分块的长文本
- 表格该用时不用
- 所有信息都加粗，导致没有重点
- 图存在，但没有文字解释

## 7. Good Output Standard

一份合格的 Markdown 文档，应该满足：

- 不看全篇也能快速扫出结构
- 不读细节也能先抓住重点
- 需要继续展开时，能顺着层级自然阅读
- 适合后续直接进入主档或评审材料

## 8. Next Suggested Actions

完成文档初稿后，推荐自查：

1. 标题层级是否稳定
2. 表格和列表是否用在该用的地方
3. 图是否有解释文字
4. 重点是否真正高亮出来
5. 文档是否适合给业务方和评审方直接阅读
